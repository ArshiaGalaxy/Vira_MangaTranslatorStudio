# استودیو ترجمه ویرا — الگوریتم‌ها و خط لوله پردازش (نسخه آموزشی)

> **مخاطبان:** دانشجویانی که با مبانی Python و JavaScript آشنا هستند و می‌خواهند بفهمند
> یک برنامه هوش مصنوعی واقعی، از ابتدا تا انتها، چگونه مهندسی می‌شود.
>
> **هدف:** پس از مطالعه این سند، دانشجو باید بتواند کل خط لوله پردازش را از حافظه ترسیم کند،
> ورودی و خروجی هر مرحله را توضیح دهد، بدون سردرگمی فایل‌های منبع را بخواند و خطاهای رایج را
> عیب‌یابی کند.

## ۰. روش استفاده از این سند در کلاس

برنامه آموزشی پیشنهادی (۲ جلسه حدوداً ۹۰ دقیقه‌ای یا ۴ جلسه ۴۵ دقیقه‌ای):

| جلسه | موضوع | فعالیت دانشجویان |
|---|---|---|
| ۱ | تصویر کلی، مدل داده و سیستم وظایف | ترسیم نمودار جعبه‌ها و پیکان‌ها از حافظه |
| ۲ | خط لوله OCR (تشخیص حالت، قطعه‌بندی، خوشه‌بندی، حذف تکرار، ادغام بین صفحات) | دنبال‌کردن مسیر یک صفحه در کد با دیباگر |
| ۳ | ترجمه، ویرایش و بازسازی تصویر (Inpainting) | توضیح اینکه چرا ترجمه به‌صورت دسته‌ای و JSON انجام می‌شود و چرا ماسک‌ها از چندضلعی‌ها ساخته می‌شوند |
| ۴ | رندر، خروجی‌گرفتن و حالت‌های شکست | اجرای یک PDF کوچک از ابتدا تا انتها و خواندن خط‌به‌خط گزارش وظیفه |

**قاعده اول تخته:** پیش از آنکه کد را به دانشجو نشان دهید، مطمئن شوید می‌تواند تبدیل داده را در یک جمله توضیح دهد؛ مثلاً: «صفحه PDF ← فهرستی از کادرهای متن به‌همراه نوشته‌های داخل آن‌ها».

## ۱. سیستم چه کاری انجام می‌دهد؟

کاربر یک فایل PDF کمیک/مانگا/مانهوا بارگذاری می‌کند یا تصاویر فصل را وارد می‌کند. سیستم کارهای زیر را انجام می‌دهد:

1. محل نوشته‌ها را با OCR تشخیص می‌دهد و خطوط شناسایی‌شده را در بلوک‌های گفت‌وگو گروه‌بندی می‌کند.
2. در صورت تمایل، هر بلوک را با کمک یک مدل زبانی بزرگ (LLM) به فارسی ترجمه می‌کند.
3. به کاربر اجازه می‌دهد کادرها و ترجمه‌ها را در یک ویرایشگر بصری اصلاح کند.
4. نوشته اصلی را از تصویر پاک می‌کند (Inpainting).
5. ترجمه فارسی را با یک فونت فارسی، دوباره در همان محدوده رسم می‌کند.
6. خروجی را به‌شکل PDF، فایل ZIP حاوی WebP یا PSD لایه‌باز صادر می‌کند.

تمام پردازش‌ها به‌صورت محلی اجرا می‌شوند؛ تنها فراخوانی اختیاری API ترجمه به اینترنت نیاز دارد.

## ۴. مدل داده

### ۴.۱ موجودیت‌های پایگاه داده

```text
Project (1) ───< Page (1) ───< TextBlock
    │              │
    │              └──< MaskMark
    ├──< Job
    └──< GlossaryEntry
```

| موجودیت | مفهوم | فیلدهای مهم |
|---|---|---|
| `Project` | یک PDF، فصل یا مجموعه | `status`، `pdf_type` (مانگا/مانهوا)، `uses_page_sources`، نسخه‌های ذخیره‌شده تنظیمات و شمارنده‌ها |
| `Page` | یک تصویر در خط لوله پردازش | `page_number`، `width`، `height` |
| `TextBlock` | یک ناحیه دیالوگ یا افکت صوتی | `key`، `original_text`، `translation`، `block_type`، کادر محدودکننده `(x1,y1,x2,y2)`، چندضلعی‌های `text_boxes`، بازنویسی‌های سبک، `rotation` و `orientation` |
| `Job` | یک عملیات زمان‌بر | `kind`، `status`، `progress`، `stage`، `logs`، `params` و `result` |
| `MaskMark` | حرکت آزاد قلم پاک‌کن | نقاط `points` برحسب پیکسل تصویر |
| `GlossaryEntry` | ترجمه یکدست نام‌ها و اصطلاحات | `source` ← `target` |

### ۴.۲ ماشین حالت وضعیت پروژه

```text
created ──extract──► extracting ──success──► ready
   ▲                     │                    │
   │                     └──failure──► failed│
   │                                          │
   ├────────────── translate ────────────────►│
   │                                          │
   ├────────────── apply/clean/render ───────►│
   │                                          │
   └────────────── reset/cancel ──────────────┘
```

وضعیت‌های `TRANSLATING` و `APPLYING` موقتی هستند؛ وظایف معمولاً دوباره به `READY` برمی‌گردند و عملیات `APPLY` در وضعیت `DONE` پایان می‌یابد.

### ۴.۳ ماشین حالت وظیفه

```text
pending ──► running ──► success
   │           │
   │           ├──► failed
   │           └──► cancelled
   └──► cancelled
```

رکورد `Job` تنها مرجع معتبر برای نوار پیشرفت رابط کاربری است. رشته پردازشگر، مقادیر `progress` (از ۰ تا ۱)، `stage` (توضیح قابل فهم برای انسان) و `logs` (۴۰۰ خط آخر) را می‌نویسد.

### ۴.۴ فایل‌ها کجا ذخیره می‌شوند؟

```text
media/projects/<project-uuid>/
├── pages/page-N.jpg        تصویر استانداردشده صفحه (فضای مختصات OCR و ویرایشگر)
├── cleaned/page-N.jpg      پس از بازسازی و حذف متن اصلی
├── rendered/page-N.jpg     پس از رسم متن فارسی
├── outputs/*.pdf|*.zip     خروجی‌های نهایی
├── sources/page-N.jpg      مجموعه صفحات نگهداری‌شده (در صورت ویرایش)
```

**اصل ثابت مختصات:** تمام مختصات `TextBlock` در فضای پیکسلی تصویر متناظر با `pages/page-N.jpg` بیان می‌شوند. ویرایشگر، OCR، بازسازی تصویر و رندر همگی از همین فضای واحد استفاده می‌کنند. نقض این اصل، رایج‌ترین علت خطاهایی است که در آن‌ها «متن در جای اشتباه ظاهر می‌شود».

## ۵. سیستم وظایف (اجرای عملیات زمان‌بر)

### ۵.۱ چرا به وظایف پس‌زمینه نیاز داریم؟

OCR، بازسازی تصویر و ترجمه LLM ممکن است از چند ثانیه تا چند دقیقه طول بکشند. یک درخواست HTTP معمولی نباید این مدت مسدود بماند. بنابراین API بلافاصله پاسخ `202 Accepted` را همراه با یک شیء `Job` برمی‌گرداند و فرانت‌اند با درخواست `GET /api/jobs/<id>` وضعیت را دوره‌ای بررسی می‌کند.

### ۵.۲ الگوریتم ثبت وظیفه (`studio/jobs.py`)

```text
submit_job(project, kind, params, run):
    lock = per_project_lock(project.id)
    if not lock.acquire(blocking=False):
        raise "Another job is already running"
    job = Job.objects.create(project, kind, params)
    cancel_event = event_for(job.id)
    start daemon thread:
        ctx = JobContext(job)
        try:
            ctx.progress(0, "Starting")
            result = run(ctx)
            ctx.check_cancelled()
            ctx.succeed(result)
        except JobCancelled:
            finalize row as CANCELLED
            settle project to READY or CREATED
        except Exception as e:
            sync counters from partial work
            ctx.fail(traceback)
            project.status = FAILED
        finally:
            remove cancel event
            release lock
```

جزئیات مهم مهندسی که ارزش آموزش دارند:

- **فقط یک وظیفه سنگین برای هر پروژه:** این محدودیت با قفل درون‌فرایندی اعمال می‌شود، نه با یک پرچم در پایگاه داده.
- **رقابت بر سر نوشتن در SQLite:** نوشتن گزارش پیشرفت و لاگ‌ها با مکث تصاعدی دوباره امتحان می‌شود (`_db_write_retry`).
- **لغو مشارکتی است:** تابع `ctx.check_cancelled()` در نقاط حساس (گزارش پیشرفت، پردازش هر صفحه و هر مؤلفه بازسازی تصویر) فراخوانی می‌شود. یک درخواست HTTP مسدودشده به LLM قابل قطع نیست، اما به‌محض بازگشت پاسخ، وظیفه متوقف می‌شود.
- **محافظت از وضعیت‌های پایانی:** `progress()` فقط رکوردهایی را به‌روزرسانی می‌کند که هنوز در وضعیت `PENDING` یا `RUNNING` هستند؛ بنابراین یک گزارش پیشرفت دیرهنگام نمی‌تواند وظیفه لغوشده را دوباره فعال کند.
- **ترمیم وظایف زامبی:** اگر سرور راه‌اندازی مجدد شود، رکورد وظیفه فعال باقی می‌ماند اما دیگر رشته پردازشگری قفل را در اختیار ندارد. `settle_zombie()` حالت «رکورد فعال + قفل آزاد» را تشخیص می‌دهد و آن را ناموفق علامت‌گذاری می‌کند تا پروژه برای همیشه قفل نشود.

### ۵.۳ انواع وظایف

| نوع | اجراکننده | اثر |
|---|---|---|
| `extract` | `run_extract` | تبدیل PDF به صفحات و بلوک‌های OCR |
| `translate` | `run_translate` | تبدیل بلوک‌ها به ترجمه فارسی |
| `clean` | `run_clean` | فقط بازسازی تصویر، بدون رسم متن |
| `render` | `run_render_text` | فقط رسم متن (در صورت نیاز ابتدا پاک‌سازی می‌کند) |
| `apply` | `run_apply` | بازسازی تصویر + رندر + تولید فایل‌های خروجی |
| `reocr` | `run_reocr` | اجرای دوباره OCR برای یک صفحه با کیفیت بالاتر |
| `import_pages` | `run_import_pages` | دانلود تصاویر فصل به‌عنوان صفحات |

## ۷. مرحله اول — تحلیل سند و انتخاب حالت

**فایل:** `comic_translator/document_analyzer.py`

### ۷.۱ هدف

مانهوا اغلب به شکل تصاویر بسیار بلند وب‌تونی منتشر می‌شود. اجرای OCR و بازسازی تصویر روی یک تصویر ۱۲۰۰×۲۰۰۰۰ هم کند است و هم حافظه زیادی مصرف می‌کند. تحلیل‌گر تصمیم می‌گیرد سند به‌صورت یک نوار بلند پردازش شود یا مانند صفحات معمولی.

### ۷.۲ الگوریتم

برای هر صفحه PDF، فقط ابعاد آن خوانده می‌شود (`page.rect`؛ بدون رندر تصویر):

```python
widths[i], heights[i] = page dimensions
avg_w = mean(widths)
avg_h = mean(heights)
avg_ar = avg_h / avg_w

areas[i] = widths[i] * heights[i]
size_consistency = std(areas) / mean(areas)  # ضریب تغییرات

long_strip_count = count(pages where height/width > long_strip_aspect_ratio_threshold)
long_strip_ratio = long_strip_count / total_pages

mode = LONG_STRIP
       if long_strip_ratio > 0.6 AND avg_ar > threshold
       else STANDARD
```

آستانه پیش‌فرض `1.5` است. قانون ۶۰ درصد مانع از آن می‌شود که وجود چند صفحه غیرمعمول، کل سند را به‌اشتباه وارد حالت نوار بلند کند.

### ۷.۳ اهمیت این انتخاب

| حالت | مفهوم Page | راهبرد OCR |
|---|---|---|
| `STANDARD` | هر `Page` برابر یک صفحه PDF است | تقسیم و OCR جداگانه هر صفحه + ادغام بین صفحات |
| `LONG_STRIP` + manga | هر `Page` برابر یک صفحه PDF است | بازگشت به مسیر استاندارد |
| `LONG_STRIP` + manhwa | هر `Page` یک **قطعه نمایشی** است، نه یک صفحه PDF | یک نوار متصل‌شده و OCR قطعه‌ای |

**نکته آموزشی:** در حالت مانهوا، تعداد ردیف‌های `Page` برابر تعداد قطعه‌ها است، نه تعداد صفحات PDF. این کار عمدی است: ویرایشگر و صادرکننده خروجی با برش‌های تصویری قابل مدیریت کار می‌کنند و ZIP نهایی WebP دوباره آن‌ها را به یک نوار بلند تبدیل می‌کند.

## ۸. مرحله دوم — خط لوله OCR

### ۸.۱ حالت استاندارد (`detect_page`)

**فایل‌ها:** `ocr_pipeline/ocr_pipeline.py`، `ocr_pipeline/page_splitter.py`

```python
detect_page(image, config, page_index):
    splitter = PageSplitter(max_chunk_height=config.max_chunk_height,
                            chunk_overlap=0)
    chunks = splitter.split(image)

    all_items = []
    for chunk in chunks:
        items = OCRProcessor.process_chunk(chunk.image, config,
                                           y_offset=chunk.y_offset)
        all_items.extend(items)

    items = DuplicateDetector.remove(all_items)
    dialogs = _cluster_items(items, config)  # DBSCAN + merge
    blocks = [Block.from_ocr(page_index, d) for d in dialogs]
    return PageResult(page, blocks, items)
```

#### ۸.۱.۱ الگوریتم قطعه‌بندی (`PageSplitter`)

```python
if height <= max_chunk_height: return [whole image]

step = max_chunk_height - overlap
y = 0
while y < height:
    end = y + max_chunk_height
    if end >= height: emit (y, height); break
    emit (y, end)
    y += step
ensure last chunk reaches height
```

هم‌پوشانی باعث می‌شود خط متنی‌ای که روی مرز دو قطعه قرار گرفته، دست‌کم در یکی از قطعه‌ها به‌طور کامل دیده شود. تشخیص‌های تکراری ناشی از هم‌پوشانی، بعداً حذف می‌شوند.

در OCR استاندارد هر صفحه، هم‌پوشانی **صفر** است؛ در اتصال تصاویر مانهوا، مقدار آن `manhwa_concat_overlap` (پیش‌فرض **۵۰۰ پیکسل**) است.

#### ۸.۱.۲ فراخوانی OCR (`ocr.py`)

```python
_ocr_single_image(image, config):
    if max_side > config.ocr_max_side:
        downscale, remember scale
    contrast × 1.3
    save temporary JPEG (quality 95)
    result = PaddleOCR.predict(path)
    convert PaddleOCR 3.x dict → [(box, (text, score))]
    filter score < confidence_min or empty text
    map boxes back to original scale
    return [OCRItem(text, box, cx, cy, height, confidence)]
```

چرا تصویر موقت JPEG ذخیره می‌شود؟ API پایتون PaddleOCR با دریافت مسیر فایل قابل‌اعتمادتر عمل می‌کند. فایل موقت در بلوک `finally` حذف می‌شود.

#### ۸.۱.۳ بازگردانی مختصات (`CoordinateRestorer`)

برای هر قطعه، مقدار `chunk.y_offset` به تمام مختصات `y` و همچنین `cy` اضافه می‌شود. پس از این مرحله، تمام آیتم‌ها در **فضای مختصات کل صفحه** قرار دارند.

#### ۸.۱.۴ تشخیص موارد تکراری (`DuplicateDetector`)

قطعه‌های هم‌پوشان ممکن است یک خط را دوبار تشخیص دهند. تشخیص‌دهنده از الگوریتمی حریصانه شبیه NMS استفاده می‌کند:

```python
sort items by confidence descending
accepted = []
for candidate in sorted_items:
    if suppressed: continue
    accepted.append(candidate)
    for other in remaining:
        if is_duplicate(candidate, other):
            suppress(other)

is_duplicate(a, b):
    if IoU(a, b) >= iou_threshold: return True
    if center_distance(a, b) <= 30
       and text_similarity(a.text, b.text) >= 0.85
       and confidences within 30%: return True
    return False
```

شباهت متن، نسبت نرمال‌شده فاصله لون‌اشتاین است:

`1 - edit_distance / max(len(a), len(b))`

این محاسبه پس از تبدیل حروف به حروف کوچک، حذف علائم نگارشی و یکسان‌سازی فاصله‌های خالی انجام می‌شود.

**نکته آموزشی:** این الگوریتم حذف تکرار از چند نشانه استفاده می‌کند و فقط به IoU متکی نیست. کادرهای OCR ممکن است کمی جابه‌جا شوند؛ بنابراین هم‌پوشانی هندسی به‌تنهایی همه موارد تکراری واقعی را پیدا نمی‌کند.

#### ۸.۱.۵ خوشه‌بندی خطوط در بلوک‌های گفت‌وگو (`_cluster_items`)

OCR خام **خطوط متن** را برمی‌گرداند، اما کاربر **حباب‌های گفت‌وگو** را ویرایش می‌کند. بنابراین باید خطوط متعلق به یک حباب را گروه‌بندی کنیم.

```python
median_h = median(item.height)
points = [(item.cx / median_h, item.cy / median_h) for item in items]
labels = DBSCAN(eps=config.dbscan_eps, min_samples=1).fit_predict(points)
```

نرمال‌سازی با ارتفاع میانه خط باعث می‌شود مقدار `eps` نسبت به مقیاس تصویر مستقل باشد: متن در تصویر بزرگ و کوچک با پارامتر یکسان خوشه‌بندی می‌شود. مقدار پیش‌فرض `eps=2.5` یعنی «مرکز خطوطی که فاصله‌شان حدود ۲٫۵ برابر ارتفاع یک خط است».

برای هر خوشه:

- کادر محدودکننده = اجتماع کادر تمام خطوط؛
- متن = خطوط متصل‌شده با `\n` و مرتب‌شده بر اساس `cy` (ترتیب خواندن)؛
- `text_boxes` = چندضلعی هر خط (برای ساخت ماسک دقیق در مراحل بعد نگهداری می‌شوند).

سپس `_merge_nearby_dialogs` ادغام **محافظه‌کارانه‌ای** انجام می‌دهد. تمام شرط‌های زیر باید برقرار باشند:

1. هم‌پوشانی افقی حداقل ۳۰ درصد عرض کادر باریک‌تر باشد.
2. فاصله عمودی حداکثر `max(20, median_h)` باشد.
3. فاصله مراکز حداکثر `max(50, 3 * median_h)` باشد.
4. نسبت ارتفاع خطوط حداقل `0.85` باشد (اندازه فونت مشابه).
5. اختلاف زاویه از آستانه کمتر یا مساوی باشد (اگر آستانه صفر باشد، غیرفعال است).
6. متن بلوک بالایی با علامت پایان جمله (`. ! ?`) تمام **نشده** باشد؛ یعنی احتمالاً جمله ناتمام است.

اگر دو بلوک ادغام شوند، متن آن‌ها با یک خط جدید به هم متصل و کادرهایشان با هم ادغام می‌شود.

### ۸.۲ حالت نوار بلند مانهوا (`run_manhwa_concat_ocr`)

**فایل:** `ocr_pipeline/ocr_pipeline.py`

```text
1. تمام صفحات PDF که نباید رد شوند، با DPI تنظیم‌شده رندر می‌شوند.
2. جلدها (که از OCR کنار گذاشته می‌شوند) از صفحات محتوایی جدا می‌شوند.
3. عرض تمام صفحات محتوایی به config.manhwa_concat_width (برابر 1200) تغییر می‌کند.
4. صفحات به‌صورت عمودی به هم متصل می‌شوند → یک تصویر بسیار بلند.
5. تصویر بلند دو بار تقسیم می‌شود:
       قطعه‌های OCR:      ارتفاع = standard_max_side (3000)، هم‌پوشانی = 500
       قطعه‌های ذخیره‌سازی: ارتفاع = standard_max_side (3000)، هم‌پوشانی = 0
6. OCR روی هر قطعه اجرا و آفست y به مختصات تصویر بلند بازگردانده می‌شود.
7. حذف موارد تکراری + خوشه‌بندی DBSCAN انجام می‌شود → بلوک‌ها در مختصات تصویر بلند.
8. tall.jpg + page_offsets.json + قطعه‌های نمایشی page-1.jpg… ذخیره می‌شوند.
```

سپس `services.run_extract` هر بلوک را از مختصات تصویر بلند به مختصات محلی قطعه تبدیل می‌کند:

```python
center_y = (block.y1 + block.y2) / 2
find chunk index i such that offsets[i] <= center_y < offsets[i] + height[i]
local_x = clamp(block.x, 0, chunk_width)
local_y = block.y - offsets[i]
drop block if local width/height < 4 px
```

کلید بلوک‌ها دوباره به شکل `p{chunk}_d{n}` ساخته می‌شود. هنگام خروجی‌گرفتن، نوار بلند برای ZIP وب‌تون دوباره سرهم می‌شود.

**نکته آموزشی:** این طراحی بر پایه «استدلال سراسری، ذخیره‌سازی محلی» است. OCR کل فصل را یک‌جا می‌بیند (بنابراین حباب‌هایی که از مرز صفحات اصلی عبور می‌کنند به‌طور طبیعی یکپارچه باقی می‌مانند)، اما کاربر در قطعه‌های کوچک ویرایش و رندر انجام می‌دهد.

### ۸.۳ ادغام بین صفحات (فقط در حالت استاندارد)

**فایل‌ها:** `ocr_pipeline/cross_page_ocr.py`، `dialogue_merger.py`

برخی حباب‌ها از پایین صفحه N شروع می‌شوند و در بالای صفحه N+1 ادامه پیدا می‌کنند. پس از OCR جداگانه هر صفحه، این حباب‌ها به شکل دو بلوک دیده می‌شوند. مرحله ادغام بین صفحات تلاش می‌کند آن‌ها را به هم متصل کند.

#### ۸.۳.۱ فیلتر مرزی (بهینه‌سازی)

OCR بین صفحات پرهزینه است؛ بنابراین فقط برای جفت‌صفحه‌هایی اجرا می‌شود که دست‌کم یکی از صفحات، بلوکی در نزدیکی مرز بالا یا پایین داشته باشد:

```python
boundary_region = 200 px
block qualifies if:
    (block.y1 < 200 or block.y2 > page_height - 200)
    and block.height >= 20 px
```

اگر هیچ‌کدام از صفحات چنین بلوکی نداشته باشند، آن جفت صفحه با یک گزارش اشکال‌زدایی رد می‌شود.

#### ۸.۳.۲ اجرای OCR روی نوار مرزی

```python
bottom = crop bottom `cross_page_height` (600) of page N
top    = crop top `cross_page_height` of page N+1
resize both to common width
combined = vertical stack(bottom, top)
items = OCR(combined)

for item:
    if box crosses the seam:        → span (coordinates in page N space)
    elif item ends above seam:      → page N item
    else:                           → page N+1 item (shift y by -seam)
```

#### ۸.۳.۳ تصمیم برای ادغام (همه شرط‌ها لازم‌اند)

1. بلوک پایینی نزدیک انتهای صفحه N (فاصله حداکثر ۱۰۰ پیکسل) و بلوک بالایی نزدیک ابتدای صفحه N+1 (فاصله حداکثر ۱۰۰ پیکسل) باشد.
2. هم‌ترازی افقی وجود داشته باشد (هم‌پوشانی یا فاصله مراکز حداکثر ۸۰ پیکسل).
3. اختلاف ارتفاع حداکثر ۳۰ درصد باشد.
4. بلوک قبلاً ادغام نشده باشد (`continuation_page == 0`).
5. متن صفحه N ناقص به نظر برسد (بدون علامت پایان جمله).
6. اگر تشخیص‌های span وجود دارند، دست‌کم یکی از آن‌ها حداقل ۴۰ درصد کلمات را با **هر دو** نیمه مشترک داشته باشد (بر اساس Jaccard).

در صورت ادغام:

- متن = متن صفحه N + `\n` + متن صفحه N+1 (یا متن span، اگر طولانی‌تر و کامل‌تر باشد)؛
- کادر محدودکننده = اجتماع دو کادر؛
- `pages = [N, N+1]` و `continuation_page = N+1`؛
- بلوک ادغام‌شده به صفحه N متصل می‌شود.

## ۱۰. مرحله چهارم — ترجمه

**فایل‌ها:** `studio/services.py::run_translate` و `comic_translator/translator/`

### ۱۰.۱ انتخاب مواردی که باید ترجمه شوند

```python
query = blocks ordered by (page_number, order)
if block_ids given: restrict to those ids
if not force: only blocks with empty translation
if nothing: return immediately
```

### ۱۰.۲ الگوریتم دسته‌بندی (Batching)

```python
chunk_size = config.translator.chunk_size  # پیش‌فرض 12
for each chunk:
    batch = {block.key: block.original_text}
    context = "Context: Page 3, 4. Previous dialogs: …"
    prompt = system_prompt + glossary lines
    result = provider.translate_batch(batch, prompt, context)
    for block in chunk:
        if result[key] non-empty: save translation
        append to previous-dialogs window (last 3)
        possibly update glossary
```

چرا JSON؟ مدل یک دیکشنری `{key: text}` دریافت می‌کند و باید همان کلیدها را برگرداند. به این ترتیب ارتباط ترجمه با کادر متن حفظ می‌شود و دیگر به جداکردن شکننده متن بر اساس خطوط وابسته نیستیم.

`parse_json_response` موارد زیر را مدیریت می‌کند:

1. بلوک‌های کد Markdown (مانند ` ```json … ``` `)؛
2. متن توضیحی قبل یا بعد از شیء JSON؛
3. کلیدهای گم‌شده (با رشته خالی پر می‌شوند)؛
4. JSON خراب یا نامعتبر → استخراج عبارت‌های `"key": "value"` با Regex.

### ۱۰.۳ زمینه و واژه‌نامه

- **زمینه (Context):** شماره صفحات به‌علاوه سه ترجمه قبلی. این اطلاعات به مدل کمک می‌کند ضمیرها و لحن را در حباب‌های نزدیک به هم یکدست نگه دارد.
- **واژه‌نامه (Glossary):** نام‌ها و اصطلاحات به شکل `English → Persian` به system prompt افزوده می‌شوند. پس از هر دسته، `_update_glossary` در صورت برقرار بودن شرایط زیر یک نگاشت اضافه می‌کند:
  - ترجمه حداکثر ۸ کلمه باشد؛
  - متن مبدأ شبیه یک کلمه با حرف اول بزرگ باشد؛
  - ترجمه حداکثر ۳ کلمه باشد.

### ۱۰.۴ رفتار ارائه‌دهندگان ترجمه

| ارائه‌دهنده | نقطه پایانی | راهبرد جایگزین |
|---|---|---|
| OpenRouter | `/api/v1/chat/completions` | ابتدا مدل تنظیم‌شده و سپس حداکثر ۷ مدل گفت‌وگویی رایگان امتحان می‌شوند؛ در پاسخ 429 به `Retry-After` احترام گذاشته می‌شود |
| Gemini | Google Generative Language API | ابتدا مدل تنظیم‌شده و سپس `gemini-2.0-flash`، `-flash-lite` و `1.5-flash` امتحان می‌شوند |
| Custom | هر مسیر `/chat/completions` سازگار با OpenAI | سه تلاش (LM Studio، Ollama، vLLM یا رله‌ها) |

### ۱۰.۵ سیاست شکست جزئی

اگر یک دسته با خطا روبه‌رو شود، خطا ثبت می‌شود و حلقه ادامه پیدا می‌کند. اگر در مجموع **هیچ** بلوکی ترجمه نشود، وظیفه با یک پیام خطای قابل اقدام ناموفق علامت‌گذاری می‌شود (کلید یا نقطه پایانی را بررسی کنید). این روش بهتر از شکست‌دادن کل وظیفه به‌دلیل محدودیت نرخ یک دسته است، در حالی که دسته‌های دیگر می‌توانند موفق شوند.

### ۱۱.۲ الگوریتم تعامل با ویرایشگر

- **جابجایی:** اختلاف مختصات اشاره‌گر برحسب پیکسل تصویر به کادر محدودکننده بلوک اضافه می‌شود.

- **پاک‌کن:** علامت‌های ماسکی را که کادرشان حداکثر ۱۰ پیکسل با حرکت پاک‌کن فاصله دارد حذف می‌کند.

### ۱۱.۳ قرارداد پیش‌نمایش زنده

ویرایشگر باید دقیقاً همان چیزی را نشان دهد که رندرکننده رسم خواهد کرد. ویرایشگر بلوک‌های پیش‌نویس را به `POST /api/projects/:id/preview-layout` می‌فرستد. بک‌اند از همان توابع `resolve_style` و `text_layout` رندرکننده استفاده می‌کند و نتیجه زیر را برمی‌گرداند:

```json
{
  "block_id": {
    "font_size": 0,
    "font_url": "",
    "align": "",
    "rotation": 0,
    "lines": [{ "text": "", "x": 0, "y": 0 }]
  }
}
```

مرورگر فونت را با `FontFace` بارگذاری می‌کند و هر خط را در مختصات برگشتی رسم می‌کند. به این ترتیب لازم نیست منطق شکل‌دهی و اندازه‌گیری متن فارسی در JavaScript دوباره پیاده‌سازی شود.

**نکته آموزشی:** یک پیاده‌سازی برای اندازه‌گیری، دو مصرف‌کننده. این بهترین راه دفاع در برابر خطای «پیش‌نمایش درست است اما خروجی نهایی اشتباه است» محسوب می‌شود.

### ۱۱.۴ سازگاری هندسه و ماسک

وقتی یک بلوک جابه‌جا یا تغییر اندازه داده می‌شود، `TextBlocksView.partial_update` چندضلعی‌های OCR ذخیره‌شده در `text_boxes` را با همان ضرایب مقیاس تغییر می‌دهد:

```python
sx = new_width / old_width
sy = new_height / old_height
new_point = (new_x1 + (old_x - old_x1) * sx,
             new_y1 + (old_y - old_y1) * sy)
```

بدون این کار، بازسازی تصویر نوشته را از محل قدیمی پاک می‌کند، در حالی که متن جدید در محل تازه رسم می‌شود.

## ۱۲. مرحله ششم — بازسازی تصویر (حذف متن اصلی)

**فایل‌ها:** `studio/services.py::_inpaint_pages`، `comic_translator/inpaint.py` و پوشه `inpainters/`

### ۱۲.۱ کدام نواحی پاک می‌شوند؟

یک ناحیه زمانی پاک می‌شود که:

- بلوک ترجمه غیرخالی داشته باشد؛ و
- نوع بلوک `sfx` نباشد (افکت‌های صوتی عمداً حفظ می‌شوند)؛ و
- تمام چندضلعی‌های `MaskMark` که با دست روی آن صفحه رسم شده‌اند نیز به ماسک اضافه شوند.

اگر صفحه هیچ‌کدام از این موارد را نداشته باشد، به‌طور کامل رد می‌شود.

### ۱۲.۲ ساخت ماسک (معماری سه‌ماسکی)

`inpainters/common.py` سه نوع ماسک را از هم متمایز می‌کند:

| ماسک | کاربرد | به مدل داده می‌شود؟ |
|---|---|---|
| **Core mask (ماسک هسته)** | پیکسل‌های دقیق متن، بر اساس چندضلعی‌های OCR (یا در نبود آن‌ها کادر مستطیلی) | خیر |
| **Inference mask (ماسک استنتاج)** | ماسک هسته که چند پیکسل گسترش داده شده است (برای لبه‌های ضد‌دندانه و زمینه) | بله، به‌صورت دودویی |
| **Blend mask (ماسک ترکیب)** | ماسک نرم‌شده برای ترکیب نهایی تصویر | خیر |

اصل ثابت: **مدل‌های عصبی ماسک دودویی دریافت می‌کنند**؛ نرم‌سازی لبه‌ها فقط هنگام ترکیب نتیجه با صفحه و در حد ۱ تا ۲ پیکسل استفاده می‌شود تا هاله ایجاد نشود.

چندضلعی‌ها به مستطیل‌ها ترجیح داده می‌شوند، زیرا حباب‌های گفت‌وگو اغلب منحنی هستند یا با تصویر پس‌زمینه هم‌پوشانی دارند. هنگام جابه‌جایی بلوک، چندضلعی‌ها نیز همراه آن جابه‌جا می‌شوند (بخش ۱۱.۴).

### ۱۲.۳ انتخاب موتور و جایگزین‌ها

```python
_create_backend(method):
    try requested method
    else fallback chain:
        cv_auto  → opencv → color
        pcleaner → opencv → color
    cache backend by (method, device, pcleaner config)
```

گزارش وظیفه به‌صراحت اعلام می‌کند که آیا موتور درخواستی در دسترس نبوده و از جایگزین استفاده شده است یا خیر. این موضوع مهم است: افت بی‌صدای کیفیت یک باگ محسوب می‌شود.

### ۱۲.۴ الگوریتم `cv_auto` — موتور پیش‌فرض

**فایل:** `inpainters/cv_auto.py`

این جالب‌ترین الگوریتم پروژه است. پیش از تصمیم‌گیری درباره نحوه پرکردن ناحیه، پس‌زمینه اطراف آن را تحلیل می‌کند.

```text
ساخت ماسک ترکیبی از تمام نواحی
components = مؤلفه‌های متصل ماسک

برای هر مؤلفه:
    کادرهای متن اصلیِ هم‌پوشان را پیدا کن → کادر مرجع
    ring_thickness = محدودکردن ۳٪ بزرگ‌ترین ضلع کادر مرجع به بازه ۲ تا ۲۴
    ring = پیکسل‌های یک حلقه درست بیرون از کادر مرجع
    (modal_color, fraction) = رنگ غالبِ کوانتیزه‌شده حلقه

    اگر fraction >= solid_ratio (0.85):
        # پس‌زمینه یک‌رنگ است (معمولاً حباب گفت‌وگو)
        مؤلفه را با modal_color پر کن
        لبه‌ها را با ماسک نرم‌شده ترکیب کن
    در غیر این صورت:
        # پس‌زمینه پیچیده است (اثر هنری، گرادیان یا بافت)
        تلاش برای اجرای SimpleLaMa روی برش 512×512:
            تغییر یکنواخت مقیاس برش تا جاگرفتن در 512
            پرکردن فضای باقی‌مانده با انعکاس لبه‌ها
            اجرای مدل، برش مجدد و تغییر اندازه به ابعاد اصلی
        در غیر این صورت، اگر مساحت حفره <= 60,000 پیکسل باشد:
            پرکردن از داخل: رنگ همسایه‌های پرشده را به‌صورت تکراری
            به مرز حفره منتقل کن (بافت به سمت داخل جریان پیدا می‌کند)
        در غیر این صورت:
            از cv2.inpaint (روش Telea) استفاده کن؛ چون روش قبلی بیش از حد کند می‌شود
```

چرا از حلقه اطراف استفاده می‌کنیم، نه فضای داخلی؟ فضای داخلی حاوی خود متن است. حلقه بیرون از کادر متن معمولاً فقط پس‌زمینه حباب را دارد و بنابراین مرجع مناسبی برای رنگ پرکننده است.

چرا هر مؤلفه جداگانه پردازش می‌شود؟ دو حباب روی پس‌زمینه‌های متفاوت ممکن است به تصمیم‌های متفاوتی برای پرکردن نیاز داشته باشند.

چرا به‌جای محوکردن (Blur) از روش پرکردن به داخل استفاده می‌شود؟ محوکردن روی تصاویر نیم‌سایه یا طراحی خطی، لکه‌ای قابل مشاهده ایجاد می‌کند. روش پرکردن به داخل، پیکسل‌های واقعی همسایه را به سمت داخل کپی می‌کند و بافت را حفظ می‌کند.

### ۱۲.۵ موتورهای دیگر

| موتور | الگوریتم | کاربرد |
|---|---|---|
| `color` | پرکردن با رنگ نمونه‌برداری‌شده از داخل/پس‌زمینه | سریع‌ترین و کم‌کیفیت‌ترین؛ همچنین آخرین جایگزین |
| `opencv` | روش Navier–Stokes (`ns`) یا Telea | همیشه در دسترس |
| `pcleaner` | ابزار خط فرمان خارجی PanelCleaner: تشخیص متن + ساخت ماسک + بازسازی تصویر | در صورت نصب‌بودن |

### ۱۲.۶ جایگزین در سطح سرویس

اگر `inpaint_batch` برای یک صفحه خطا بدهد، `_inpaint_pages` خطا را می‌گیرد، آن را ثبت می‌کند و برای هر ناحیه `erase_region` را با پرکردن رنگی اجرا می‌کند. وظیفه ادامه پیدا می‌کند و صفحه همچنان قابل استفاده باقی می‌ماند.

## ۱۳. مرحله هفتم — رندر متن فارسی

**فایل:** `comic_translator/renderer.py`

### ۱۳.۱ تعیین سبک

`resolve_style(text_type, config, overrides…)` تنظیمات را به ترتیب زیر ادغام می‌کند:

1. **مقادیر پیش‌فرض نوع متن** (`TYPE_DEFAULTS`):
   - `dialog`: فونت Mikhak، اندازه ۱۰۰٪، وسط‌چین
   - `sfx`: فونت AFSANEH، اندازه ۱۰۰٪
   - `think`: فونت AFSANEH، اندازه ۸۵٪، دورخط نازک‌تر
   - `action`: فونت Mikhak، اندازه ۱۲۰٪، دورخط ضخیم‌تر
   - `whisper`: فونت Vazir، اندازه ۸۰٪، خاکستری
   - `narration`: فونت Mikhak، راست‌چین و راست‌به‌چپ (RTL)
   - `system`: فونت Vazir، اندازه ۹۰٪، آبی
2. **بازنویسی‌های مخصوص هر بلوک:** رنگ، رنگ/اندازه دورخط، تراز، فونت و حداکثر اندازه.
3. **تنظیمات سراسری فونت:** محدوده اندازه و ضخامت پیش‌فرض دورخط.

### ۱۳.۲ الگوریتم تنظیم اندازه فونت

```python
text_layout(text, box_w, box_h, …):
    font_path = explicit override or find_font(type)
    effective_max = max(size_min, size_max * size_factor or block override)
    font, lines, size = fit_font_size(text, font_path, box_w, box_h,
                                      effective_max, size_min)
    measure multiline bbox with the final font
    return font, lines, size, spacing, bbox, alignment
```

تابع `fit_font_size`:

```python
size = size_max
while size > size_min:
    font = load_font(path, size)
    lines = wrap(text, font, box_w - 8)
    estimated_height = spacing*(n-1) + n*size*2
    if estimated_height <= box_h: return
    size -= 2
return size_min  # حداقل قطعی، حتی اگر متن از کادر بیرون بزند
```

تصمیم طراحی: **کار از حداکثر اندازه تنظیم‌شده توسط کاربر شروع می‌شود** و فقط در صورت نیاز اندازه کاهش می‌یابد. مشخصات تایپوگرافی می‌گوید کوچک‌کردن فونت باید آخرین راه‌حل باشد؛ این پیاده‌سازی آن را به شکل «شروع با اندازه بزرگ و کاهش تدریجی» اجرا می‌کند.

### ۱۳.۳ شکستن خطوط

`_wrap_text` از روش حریصانه شکستن خطوط بر اساس **عرض اندازه‌گیری‌شده برحسب پیکسل** استفاده می‌کند، نه تعداد کاراکترها؛ شکست‌های صریح `\n` را حفظ می‌کند و کلمات را با خط تیره نمی‌شکند.

### ۱۳.۴ الگوریتم انتخاب رنگ متن

اولویت‌ها:

1. رنگ صریح تعیین‌شده برای همان بلوک؛
2. رنگ ثابت پیش‌فرض نوع متن (مثلاً خاکستری برای whisper و آبی برای system)؛
3. رنگ متن اصلی که **پیش از بازسازی تصویر** نمونه‌برداری شده است؛
4. رنگ جایگزین سیاه یا سفید برای ایجاد کنتراست.

نمونه‌برداری رنگ متن اصلی (`_sample_original_text_color`):

```text
تخمین رنگ پس‌زمینه (داخل ناحیه در صورت یکنواخت‌بودن، وگرنه حلقه اطراف)
محدودکردن پیکسل‌ها به چندضلعی‌های متن OCR (یا کادر کوچک‌شده)
نگه‌داشتن فقط پیکسل‌های جوهر: مجموع |pixel - background| > 90
کوانتیزه‌کردن رنگ‌های جوهر و بازگرداندن پرتکرارترین دسته
```

سپس `_adjust_color_contrast` کنتراست WCAG را در برابر پس‌زمینه پاک‌سازی‌شده به حداقل ۳٫۰ می‌رساند. این تابع فقط **روشنایی** را با گام‌های کوچک تغییر می‌دهد و فام رنگ را حفظ می‌کند. اگر هیچ مقدار روشنایی به هدف نرسد، بر اساس درخشندگی، سیاه یا سفید انتخاب می‌شود.

### ۱۳.۵ دورخط (Stroke)

اگر ضخامت دورخط بیشتر از صفر باشد:

- در صورت وجود، رنگ صریح دورخط استفاده می‌شود؛
- در غیر این صورت، برای متن تیره دورخط سفید و برای متن روشن دورخط سیاه انتخاب می‌شود.

این کار خوانایی متن را روی آثار تصویری حفظ می‌کند.

### ۱۳.۶ چرخش و متن عمودی

- **چرخش:** متن روی یک لایه شفاف به اندازه کادر رسم می‌شود، به‌اندازه `-rotation` می‌چرخد (PIL خلاف جهت عقربه‌های ساعت می‌چرخاند، در حالی که رابط کاربری جهت ساعت‌گرد دارد) و در مرکز قرار می‌گیرد. چرخاندن کل کادر، نسبت به چرخاندن یک برش فشرده از حروف، تراز را بهتر حفظ می‌کند.
- **حالت عمودی:** متن به‌شکل معمول روی یک لایه شفاف رسم می‌شود، ۹۰ درجه در جهت منفی می‌چرخد و در مرکز قرار می‌گیرد. (صفحه‌آرایی واقعی ستون عمودی فارسی خارج از محدوده این پروژه است.)

> نکته برای دانشجویان پیشرفته: تابع `_reshape_persian` در حال حاضر کاری انجام نمی‌دهد. شکل‌دهی صحیح فارسی از طریق نسخه Pillow/FreeType دارای پشتیبانی libraqm انجام می‌شود. اگر حروف جدا از هم نمایش داده شدند، اولین موردی که باید بررسی شود ساخت Pillow و پشتیبانی libraqm است، نه این تابع.

### ۱۳.۷ درج شناسه فصل

`draw_chapter_id` گوشه‌ها را به ترتیب زیر امتحان می‌کند: بالا-راست، بالا-چپ، پایین-راست و پایین-چپ. اولین گوشه‌ای انتخاب می‌شود که با هیچ‌یک از کادرهای متن رندرشده هم‌پوشانی نداشته باشد. این نمونه ساده اما جالبی از جای‌گذاری بر اساس محدودیت‌ها است.

### ۱۳.۸ راهبرد حافظه برای صفحات بلند

`render_on_tall_image` صفحات را به دسته‌هایی با اندازه `config.font.tall_render_chunk_size` (پیش‌فرض ۳) تقسیم می‌کند، فقط همان دسته را به هم متصل می‌کند، نواحی متقاطع با آن را رندر می‌کند، دوباره جدا می‌کند و حافظه دسته را آزاد می‌کند. بنابراین در هر لحظه فقط بخشی از فصل در حافظه قرار دارد. کش `_np_array_cache` پس از هر قطعه پاک می‌شود، چون ممکن است مقدارهای `id()` دوباره استفاده شوند.

## ۱۴. مرحله هشتم — خروجی‌گرفتن

**فایل‌ها:** `studio/services.py::run_apply`، `comic_translator/pdf.py` و `psd_export.py`

### ۱۴.۱ خط لوله Apply

```text
1. ساخت بلوک‌های موتور از پایگاه داده + نقشه ترجمه‌ها.
2. برای هر صفحه، در صورت وجود rendered/page-N.jpg از همان فایل استفاده کن
   (خروجی‌گرفتن نباید کاری را که قبلاً در پیش‌نمایش انجام شده دوباره انجام دهد).
   فقط صفحاتی پردازش می‌شوند که تصویر رندرشده ندارند.
3. بارگذاری تصاویر صفحه (از pages/ یا در صورت نبود، رندر مجدد از PDF).
4. بازسازی نواحی‌ای که متن دریافت می‌کنند (پیشرفت ۵ تا ۴۰ درصد).
5. رندر متن (پیشرفت ۴۵ تا ۹۰ درصد).
6. ذخیره پیش‌نمایش‌های rendered/page-N.jpg.
7. خروجی‌گرفتن در قالب‌های درخواستی.
8. project.status = DONE
```

نکته ظریف و مهم: `render_page_list` تصاویر را **بر اساس موقعیت** نگاشت می‌کند (`page_num = index + 1`). چون ممکن است `run_apply` فقط زیرمجموعه‌ای از صفحات را پردازش کند، شماره صفحات در انتظار پردازش را در یک `sub_map` موقت از نو تنظیم می‌کند تا جست‌وجوی بلوک‌ها همچنان با تصاویر هماهنگ بماند.

### ۱۴.۲ قالب‌های خروجی

| قالب | روش | توضیحات |
|---|---|---|
| **PDF** | تبدیل هر تصویر به JPEG با کیفیت ۷۵ و سپس ساخت صفحه با PyMuPDF | یک صفحه PDF برای هر صفحه خط لوله |
| **ZIP (معمولی)** | تغییر عرض هر صفحه به ۱۲۰۰، ذخیره WebP با کیفیت ۹۵ و تقسیم ارتفاع‌های بیشتر از ۸۱۹۲ | فایل‌هایی مانند `page_001.webp` و… |
| **ZIP (وب‌تون)** | اتصال تمام قطعه‌های رندرشده به یک تصویر بلند و سپس ساخت ZIP حاوی WebP | تجربه مطالعه نوار بلند را حفظ می‌کند |
| **PSD** | یک PSD برای هر صفحه: لایه `Background` به‌علاوه یک لایه متن RGBA برای هر بلوک ترجمه‌شده | نام لایه‌ها بر اساس کلید بلوک؛ تغییر اندازه صفحه به عرض ۱۲۰۰ پیکسل |

### ۱۴.۳ الگوریتم لایه‌های PSD

```text
تغییر اندازه صفحه به عرض 1200؛ مقیاس‌دادن تمام مختصات بلوک‌ها با همان ضریب
PSD = سند RGB جدید
افزودن لایه Background (صفحه رندرشده)
برای هر بلوک ترجمه‌شده:
    فقط متن همان بلوک را روی یک لایه شفاف RGBA تمام‌صفحه رندر کن
    آن را با نام کلید بلوک به‌عنوان یک لایه اضافه کن
تمام فایل‌های PSD را در یک ZIP ذخیره کن
```

به این ترتیب کاربر می‌تواند لایه‌های متن را با دقت پیکسلی در نرم‌افزار ویرایش تصویر تغییر دهد.

## ۱۵. سیستم پیکربندی

**فایل‌ها:** `studio_engine/config.py` و `studio/services.py`

### ۱۵.۱ دو سطح تنظیمات

```text
GlobalSetting("config")  ──►  مقادیر پیش‌فرض برای هر پروژه جدید
        │
        └──► کپی در Project.{ocr,font,inpaint,translator,chapter_id}_config
                          │
                          └──► ادغام با تنظیمات سراسری هنگام اجرای وظیفه
                               (مقادیر پروژه اولویت دارند)
```

قواعد ادغام (`_get_config`):

- دیکشنری‌های تو در تو، کلیدبه‌کلید ادغام می‌شوند؛
- یک رشته خالی در snapshot پروژه، مقدار سراسری غیرخالی را بازنویسی نمی‌کند (بنابراین اگر بعداً کلید API اضافه شود، پروژه‌های قدیمی نیز از آن استفاده می‌کنند)؛
- تمام تنظیمات با `_build_config` دوباره به Dataclassهای تغییرناپذیر تبدیل می‌شوند.

### ۱۵.۲ اولویت متغیرهای محیطی

در صورت غیرخالی‌بودن، متغیرهای `OPENROUTER_API_KEY`، `GEMINI_API_KEY`، `CUSTOM_*`، `OCR_DPI`، `INPAINT_METHOD` و `TRANSLATOR_PROVIDER` بر مقادیر فایل/پایگاه داده اولویت دارند.

### ۱۵.۳ سخت‌سازی امنیتی

`PUT /api/config` داده JSON خامی را از مرورگر می‌پذیرد. پیش از ادغام:

1. کلیدهای مجاز بر اساس Dataclassهای موتور تعیین می‌شوند (`_allowed_config_sections`).
2. کلیدهای ناشناخته حذف می‌شوند (`_prune_config`).
3. مسیرها اعتبارسنجی می‌شوند (`_validate_config_paths`): مسیر فونت باید داخل `FONTS_DIR` باشد و مسیر CLI مربوط به PanelCleaner باید به یک فایل موجود اشاره کند.

بدون این کنترل‌ها، یک کلاینت می‌تواند `inpaint.pcleaner_cli_path` را به یک فایل اجرایی دلخواه تغییر دهد. این مثال خوبی برای اصل «هرگز به یک بسته تنظیمات دریافتی اعتماد نکنید» است.

## ۱۶. هم‌زمانی، سازگاری داده و کش

### ۱۶.۱ قفل‌ها

| قفل | محدوده | محافظت از |
|---|---|---|
| `_project_locks[id]` | یک فرایند | فقط یک وظیفه سنگین برای هر پروژه |
| `_locks_guard` | یک فرایند | ایجاد نقشه قفل‌ها |
| `_cancel_guard` | یک فرایند | نقشه رویدادهای لغو |
| `_lama_lock` | یک فرایند | ساخت تنبل SimpleLaMa |
| `_gemini_global_lock` | یک فرایند | چون `genai.configure()` در سطح فرایند سراسری است |

### ۱۶.۲ تراکنش‌ها

- حذف پروژه و ذخیره بلوک‌ها از `transaction.atomic()` استفاده می‌کنند.
- پاک‌سازی داده‌های قبلی استخراج درون تراکنش انجام می‌شود؛ اما مرحله طولانی OCR عمداً **خارج از تراکنش** است تا SQLite برای چند دقیقه قفل نشود.
- پاک‌سازی فایل‌هایی که باید پس از ثبت تراکنش در پایگاه داده انجام شود، با `transaction.on_commit` اجرا می‌شود.

### ۱۶.۳ کش‌ها

| کش | کلید | زمان/روش بی‌اعتبارسازی |
|---|---|---|
| `_ocr_cache` | تاپل تنظیمات OCR | در طول عمر فرایند (تغییر تنظیمات → کلید جدید) |
| `_backend_cache` | روش + دستگاه + تنظیمات pcleaner | در طول عمر فرایند |
| `_font_cache` | `(path, size)` | در طول عمر فرایند؛ خطاها کش نمی‌شوند |
| `_np_array_cache` | `id(image)` + بررسی هویت شیء | بی‌اعتبارسازی صریح پس از رسم/پاک‌کردن؛ پس از قطعه‌های بلند پاک می‌شود |
| `_free_models` | نمونه ارائه‌دهنده | برای هر نمونه |

**نکته آموزشی:** کش‌کردن بر اساس `id()` خطرناک است، زیرا پایتون ممکن است پس از جمع‌آوری زباله، شناسه‌ها را دوباره استفاده کند. کد `(image_reference, array)` را ذخیره می‌کند و پیش از استفاده از کش، هویت شیء را بررسی می‌کند؛ این الگو ارزش بررسی و بحث دارد.

## ۱۷. حالت‌های شکست و راهنمای عیب‌یابی

| نشانه | علت احتمالی | محل بررسی |
|---|---|---|
| وظیفه استخراج بلافاصله شکست می‌خورد | وابستگی‌های هوش مصنوعی نصب نیستند (`paddleocr`، `paddlepaddle`، `PyMuPDF`) | `error_message` وظیفه و `requirements-ai.txt` |
| OCR چیزی پیدا نمی‌کند | صفحه جلد یا صفحه ردشده است؛ آستانه اطمینان بیش از حد بالاست؛ تصویر کوچک است | `confidence_min`، `text_rec_score_thresh`، `ocr_det_*`؛ اجرای دوباره OCR با کیفیت `high` یا `ultra` |

| یک حباب در دو صفحه به دو بلوک تبدیل شده است | فیلتر مرزی ادغام بین صفحات آن را رد کرده یا معیارهای ادغام برقرار نشده‌اند | `boundary_region_height`، `enable_cross_page_merge` و قواعد `DialogueMerger` |
| متن فارسی پس از جابه‌جایی کادر در جای اشتباه است | `text_boxes` تغییر مقیاس نداده‌اند | شاخه هندسی در `TextBlocksView.partial_update` |
| پس از پاک‌سازی هنوز متن اصلی دیده می‌شود | موتور بازسازی به پرکردن رنگی برگشته؛ ماسک کوچک است؛ بلوک ترجمه ندارد | لاگ `Inpaint backend` یا `inpaint FAILED` و مقادیر `padding_x/y` |
| پس از پاک‌سازی، حباب لکه‌دار یا شبح‌مانند است | پس‌زمینه پیچیده با روش push-in/OpenCV پردازش شده؛ LaMa نصب نیست | نصب `simple_lama_inpainting` و بررسی خطوط لاگ `cv_auto` |
| حروف فارسی از هم جدا هستند یا مربع جایگزین نمایش داده می‌شود | فونت فاقد نویسه لازم است یا Pillow بدون libraqm ساخته شده؛ بازنویسی فونت اشتباه است | `backend/fonts/`، متغیر `FONT` و ساخت Pillow |

| ترجمه هیچ نتیجه‌ای برنمی‌گرداند | کلید API/مدل/نقطه پایانی اشتباه است؛ تجزیه JSON شکست خورده | خطاهای هر دسته در لاگ وظیفه، `parse_json_response` و Settings → Test Provider |
| وظیفه برای همیشه روی running می‌ماند | سرور در میانه وظیفه راه‌اندازی مجدد شده است (وظیفه زامبی) | `GET /api/jobs/<id>` و ترمیم `settle_zombie` |
| خطای `database is locked` | رقابت SQLite میان رشته پردازشگر و درخواست | `_db_write_retry`؛ از تراکنش‌های طولانی اجتناب کنید |
| حافظه هنگام پردازش وب‌تون تمام می‌شود | تصویر متصل‌شده بسیار بزرگ است | کاهش `standard_max_side` یا `manhwa_concat_width` و اندازه قطعه رندر بلند |
| PDF در ویندوز قفل می‌شود | هندل PyMuPDF باز مانده است | تمام مسیرهای `render_page` باید سند را در `finally` ببندند |

### روند عیب‌یابی برای دانشجویان

1. گزارش وظیفه را در رابط کاربری باز کنید. هر مرحله شماره صفحات، تعدادها و نام موتور را ثبت می‌کند.
2. خطا را با **یک صفحه** بازتولید کنید (`reocr`، `clean?page_number=N` و `render?page_number=N`).
3. فقط پایگاه داده را بررسی نکنید؛ فایل‌ها را نیز ببینید: `pages/page-N.jpg`، `cleaned/page-N.jpg` و `rendered/page-N.jpg`.
4. مختصات را مقایسه کنید: کادر بلوک در ویرایشگر را با تصویر واقعی روی هم قرار دهید. اگر کادر درست است اما متن اشتباه است، باگ در رندر است. اگر کادر اشتباه است، باگ در OCR یا بازگردانی مختصات است.
5. فقط پس از این مراحل سراغ کد بروید و از مرحله‌ای شروع کنید که در خط لاگ گزارش شده است.

## ۱۸. پیچیدگی و نکات عملکردی

| مرحله | پیچیدگی معمول | نکته عملی |
|---|---|---|
| رندر PDF | `O(pages)` | PyMuPDF سریع است؛ DPI عامل اصلی هزینه است |
| OCR قطعه‌ها | `O(total pixels / chunk area)` | PaddleOCR بیشترین زمان اجرا را مصرف می‌کند |
| DBSCAN | در بدترین حالت حدود `O(n²)` | `n` تعداد خطوط متن در هر صفحه است و معمولاً کمتر از ۲۰۰ است |
| حذف موارد تکراری | `O(n²)` به‌علاوه فاصله لون‌اشتاین `O(L²)` برای جفت‌های نزدیک | برای ورودی‌های اندازه صفحه مناسب است |
| ادغام بین صفحات | `O(candidates²)` برای هر جفت صفحه | فقط بلوک‌های نزدیک مرز، نامزد هستند |
| ترجمه | `O(blocks / chunk_size)` فراخوانی API | تأخیر شبکه عامل اصلی است؛ دسته‌بندی تعداد فراخوانی‌ها را کاهش می‌دهد |
| بازسازی تصویر | `O(components × region pixels)` | پرکردن به داخل مسیر کند است؛ LaMa برای GPU مناسب است |
| رندر | `O(regions × text layout)` | حلقه تنظیم فونت از اندازه حداکثر به سمت پایین حرکت می‌کند |
| خروجی | `O(pages × pixels)` | فشرده‌سازی WebP/PDF بیشترین هزینه را دارد |

قواعد سرانگشتی حافظه:

- هرگز کل فصل را به‌صورت یک تصویر در حافظه نگه ندارید، مگر اینکه مجبور باشید (OCR مانهوا این کار را با عرض ۱۲۰۰ پیکسل انجام می‌دهد؛ این یک مصالحه است).
- صفحات بلند را قطعه‌قطعه رندر کنید (`tall_render_chunk_size`).
- کش‌های NumPy را پس از عملیات سنگین آزاد کنید.

## ۲۰. تمرین‌های کلاسی

### تمرین ۱ — دنبال‌کردن مسیر یک صفحه (مبتدی)

یک صفحه انتخاب کنید و ساختار داده دقیق آن را در هر مرحله بنویسید:

```text
PDF page → PIL Image (W×H) → chunks [(y_offset, Image)] → OCRItems
→ deduped OCRItems → OCRDialog → Block → TextBlock → inpainted image
→ rendered image
```

یک مختصات واقعی نیز در نظر بگیرید و نشان دهید در هر مرحله چگونه تغییر می‌کند (یا چرا تغییر نمی‌کند).

### تمرین ۲ — به چالش کشیدن حذف‌کننده موارد تکراری (متوسط)

سه OCR item بسازید که یک تشخیص‌دهنده ساده مبتنی بر IoU آن‌ها را نگه می‌دارد، اما تشخیص‌دهنده چندمعیاره آن‌ها را حذف می‌کند. توضیح دهید کدام شرط فعال می‌شود.

### تمرین ۳ — چرا JSON؟ (متوسط)

توضیح دهید اگر ترجمه‌ها به‌صورت یک فهرست ساده از رشته‌ها و بر اساس ترتیب خواندن برگردانده می‌شدند، چه مشکلی پیش می‌آمد. دو نمونه مشخص از شکست ارائه دهید (ترجمه خالی و ادغام دو خط توسط مدل).

### تمرین ۴ — تصمیم‌گیری در بازسازی تصویر (پیشرفته)

برای یک حباب روی پس‌زمینه سفید و یک حباب روی آسمان گرادیانی، مسیر اجرای `cv_auto` را دنبال کنید. مشخص کنید کدام شاخه اجرا می‌شود، سهم تقریبی رنگ حلقه چقدر است و اگر LaMa نصب نباشد چه جایگزینی اجرا می‌شود.

### تمرین ۵ — افزودن یک قابلیت (پیشرفته)

یک دکمه `clean?page_number=N` اضافه کنید که فقط صفحه فعلی را پاک‌سازی کند. مسیر را از ابتدا تا انتها پیاده‌سازی کنید:

1. دکمه فرانت‌اند ← فراخوانی API؛
2. view ← `submit_job(CLEAN, {page_number})`؛
3. سرویس از قبل از این قابلیت پشتیبانی می‌کند — آن را بررسی کنید؛
4. رابط کاربری وضعیت وظیفه را بررسی کند و تصویر پاک‌سازی‌شده را با یک رشته revision برای بی‌اثرکردن کش تازه‌سازی کند.

### تمرین ۶ — عیب‌یابی یک اصل ثابت که عمداً شکسته شده است (پیشرفته)

`_persist_blocks` را تغییر دهید تا مختصات را در حالت صفحات استاندارد به فضای محلی قطعه تبدیل کند. علائم قابل مشاهده در ویرایشگر، پاک‌سازی و رندر را پیش‌بینی کنید. سپس آن را اصلاح کنید و توضیح دهید چرا تشخیص باگ در صفحه اول دشوار بود.

## ۲۱. واژه‌نامه

| اصطلاح | معنی |
|---|---|
| **Block (بلوک)** | یک حباب گفت‌وگو یا ناحیه متنی که کاربر ویرایش می‌کند |
| **Chunk (قطعه)** | برشی افقی از یک صفحه بلند که برای محدودکردن مصرف حافظه OCR/رندر استفاده می‌شود |
| **Long strip (نوار بلند)** | صفحه بسیار بلند به سبک وب‌تون |
| **Inpainting (بازسازی تصویر)** | پرکردن ناحیه ماسک‌شده با پس‌زمینه‌ای باورپذیر |
| **Mask (ماسک)** | تصویر دودویی که پیکسل‌های موردنظر برای حذف/پرکردن را مشخص می‌کند |
| **Core / inference / blend mask** | پیکسل‌های دقیق متن / ورودی گسترش‌یافته مدل / ماسک نرم‌شده ترکیب |
| **IoU** | نسبت اشتراک به اجتماع دو کادر |
| **DBSCAN** | خوشه‌بندی مبتنی بر چگالی؛ خطوط متن را در حباب‌ها گروه‌بندی می‌کند |
| **Levenshtein ratio** | شباهت متن بر اساس فاصله ویرایشی |
| **RTL** | نمایش نوشتار راست‌به‌چپ (فارسی) |
| **Zombie job (وظیفه زامبی)** | رکورد وظیفه‌ای که پس از ازبین‌رفتن فرایند پردازشگر، همچنان فعال مانده است |
| **Snapshot config** | نسخه‌ای از تنظیمات سراسری که هنگام ساخت پروژه برای همان پروژه ذخیره می‌شود |
